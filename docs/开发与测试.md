# 开发与测试

## 开发环境

项目使用 Rust `1.98.0`，版本由 `rust-toolchain.toml` 固定（`flake.nix`、CI workflow 与各 crate 的 `rust-version` 同步维护）。Nix flake 提供默认开发环境和静态 Debian 打包环境。

```bash
nix develop
rustc --version
cargo test --locked
```

默认开发 shell 包含 Rust（含 `x86_64-unknown-linux-musl` 与 `wasm32-unknown-unknown` target）、`git`、`iproute2`、`iptables`、`pkg-config`、`python3`、`bc`、`file`，WASM 策略 guest 工具 `wasm-tools`、`wit-bindgen` 与 `b3sum`，以及 netns 性能脚本所需的 `perf`、`iperf3`、FlameGraph、`ethtool`、`iputils`、`util-linux` 和 coreutils。静态 Debian 包需要额外的 musl、`dpkg` 和 `binutils`：

```bash
nix develop .#static -c scripts/build-deb.sh
```

没有 Nix 时，安装固定版本的 Rust、`iproute2`、`iptables`、`pkg-config`；构建 Debian 包还需要 `musl-gcc`、`dpkg-deb`、`readelf` 和常用 Unix 工具；验证 systemd unit 还需要 `systemd-analyze`。

## 本地检查

在修改 Rust 代码后执行：

```bash
nix develop -c cargo fmt --check
nix develop -c python3 scripts/check-doc-links.py
nix develop -c cargo test --locked
nix develop -c cargo clippy --locked --all-targets -- -D warnings
nix build
```

`Cargo.lock` 已提交。依赖变更必须同时提交锁文件，并使用 `--locked` 验证构建不会隐式更新依赖。

### WASM 策略 guest

WIT 单一来源是 `crates/ironet-policy-abi/wit/ironet-policy.wit`；SDK 通过
`wit-bindgen` 的 `path` 直接引用它。builtin guest、echo fixture 和
conservative fixture 使用共享 `target/` 构建，不要为 wasm32 目标执行
`cargo clean`：

```bash
nix develop -c scripts/build-policy-guest.sh
nix develop -c scripts/build-policy-guest.sh --check

nix develop -c wasm-tools validate --features component-model \
  crates/ironet-policy-builtin/builtin.wasm
nix develop -c wasm-tools component wit \
  crates/ironet-policy-builtin/builtin.wasm
```

脚本固定 `SOURCE_DATE_EPOCH`（默认取 HEAD 提交时间）、UTC、release
`opt-level=s`、`panic=abort`、LTO、单 codegen unit 和非增量编译；manifest
的 policy identity 从 `PolicySpecV1::builtin()` 读取，`built_at` 和
`source_revision` 不使用当前墙钟。产物为未签名的
`crates/ironet-policy-builtin/builtin.wasm`，部署方再用 `ironet policy sign`
签名；`builtin.wasm.blake3` 是 CI `--check` 比对的 `blake3:<hex>` sidecar。

## 测试层级

### 单元测试

```bash
nix develop -c cargo test --locked
```

覆盖 V2 Cell/PacketTrain、SessionHello、Presence、拓扑编译、FEC/Repair、自动调优、配置校验和控制状态。

### 网络命名空间集成测试

集成测试使用一个特权 Docker 实验容器；容器内部使用 Linux network namespace、veth、NAT、`tc netem` 与 TUN 组成拓扑。宿主机需要 Docker、`/dev/net/tun` 和创建特权网络命名空间的权限。

```bash
# 执行所有集成场景
tests/netns/run-all.sh

# 执行一个场景
tests/docker-product/run.sh
tests/docker-v2-sni/run.sh
```

| 场景 | 覆盖内容 |
| --- | --- |
| `docker-product` | 正式 V2 产品 CLI/daemon 的 `network create → invite → join`、IPv4/IPv6 数据面、撤销后 fail-closed 重连拒绝。 |
| `docker-v2-sni` | 正式 V2 产品 CLI/daemon 的两次真实 QUIC Initial 解密，验证唯一 `h3` ALPN、cover SNI 和错误 EndpointId 拒绝。 |

测试日志和制品保留在 `target/` 中；该目录不提交到 Git。

会话层的真实 loopback QUIC 测试覆盖 SessionHello、capability/limit 边界、错误
network secret、EndpointId 不匹配以及协商字段被篡改。p2/p6 与 wuwei-ws 的吞吐、
丢包和双端火焰图验收由受管理面的 profile 驱动单独执行。

### 真实网络测试

`tests/real/run.sh` 接受由调用方提供的主机和认证信息，用于验证 NAT 与对称网络环境。执行前先阅读脚本中的环境变量要求：

```bash
sed -n '1,240p' tests/real/run.sh
```

该脚本会部署和清理远端测试资源，结果写入 `target/`。

## 打包

生成 x86_64 musl 静态 Debian 包：

```bash
nix develop .#static -c scripts/build-deb.sh
```

默认产物：

```text
dist/ironet_0.1.0_amd64.deb
```

打包脚本也支持原生 ARM64 构建：

```bash
TARGET=aarch64-unknown-linux-musl scripts/build-deb.sh
# dist/ironet_0.1.0_arm64.deb
```

默认在对应架构的原生 Linux runner 上构建；交叉构建时可通过
`CC_aarch64_unknown_linux_musl` 指定 ARM64 musl 编译器。

构建脚本会：

1. 编译 `ironet` 和 `ironetd`；
2. 检查两个二进制没有动态链接器；
3. 写入 systemd unit、sysusers、sysctl、配置示例、README、许可证和 `docs/`；
4. 生成并检查 Debian 包元数据和文件列表。

验证现有包：

```bash
dpkg-deb --info dist/*.deb
dpkg-deb --contents dist/*.deb
tests/deployment/package.sh dist/*.deb
```

## CI 与发布

Forgejo 工作流位于 `.forgejo/workflows/`：

- `ci.yml`：所有分支推送和合并请求执行格式与文档链接检查、单元测试、Clippy、静态 Debian 打包与包布局验证；具备特权条件的 runner 执行全部网络命名空间场景。
- `release.yml`：推送 `v*` 标签时，验证标签与 `Cargo.toml` 版本一致，构建包和校验和，并通过 `scripts/publish-forgejo-release.sh` 发布制品。

发布版本时：

```bash
# 先完成本地检查和包验证
git tag -a v0.1.0 -m "v0.1.0"
git push origin v0.1.0
```

发布 runner 需要提供 `FORGEJO_TOKEN`，并由 Forgejo 注入 `FORGEJO_API_URL`、`FORGEJO_REPOSITORY` 和 `FORGEJO_REF_NAME`。发布脚本拒绝标签版本与 `Cargo.toml` 不一致的情况。

GitHub Actions 工作流位于 `.github/workflows/`：

- `ci.yml`：分支推送和 Pull Request 运行格式、文档、单元测试与 Clippy，并在 `ubuntu-24.04` 和 `ubuntu-24.04-arm` 原生 runner 上分别构建 `amd64`、`arm64` Debian 包；
- `release.yml`：推送与 `Cargo.toml` 版本一致的 `v*` 标签时，执行完整验证、双架构打包、包布局检查、构建来源证明、统一 `SHA256SUMS`，并发布到 GitHub Release；手动触发只生成 Actions 制品，不创建 Release。

GitHub 发布使用内置 `GITHUB_TOKEN`，无需额外配置发布密钥。仓库需要允许工作流拥有写入 Release 的权限；工作流本身已按 job 限定为最小权限。

## Vendored QUIC forks

V2 使用三个受版本控制的上游发布基线，而不是依赖开发机 Cargo cache：

| 目录 | 上游发布基线 | 上游仓库 |
| --- | --- | --- |
| `crates/iroh-v2` | `iroh 1.0.3` | `https://github.com/n0-computer/iroh` |
| `crates/noq-v2` | `noq 1.1.1` | `https://github.com/n0-computer/noq` |
| `crates/noq-proto-v2` | `noq-proto 1.1.1` | `https://github.com/n0-computer/noq` |

目录保留 crates.io 发布包的标准化 `Cargo.toml` 和原始 `Cargo.toml.orig`，Ironet 的差异直接在 fork 上审查。嵌套 `target/` 被根 `.gitignore` 排除。修改 `noq-proto`（尤其拥塞控制与 qlog 条件代码）后追加执行：

```bash
cargo test --manifest-path crates/noq-proto-v2/Cargo.toml
cargo check --features qlog --manifest-path crates/noq-proto-v2/Cargo.toml
```

## 变更维护

涉及配置、控制接口、状态 JSON、Prometheus 指标或 wire format 时，应同步更新：

- `config/example.toml`；
- README 和 `docs/`；
- 对应单元或网络命名空间测试；
- 协议或部署兼容性说明。

详细提交与审查要求见 [`CONTRIBUTING.md`](../CONTRIBUTING.md)。
